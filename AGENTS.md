# ClipNest continuation rules

These project instructions carry the user's requested workflow into another coding environment. Follow the platform's governing instructions and the user's latest authorized scope.

## Limited external execution profile — latest user direction

Engineering ownership stays in the original project chat. When assigned E01/CLOUD_TEST_ONLY_PROMPT.md, act only as an executor: read this file and docs/EXTERNAL_EXECUTION.md, run the specified prepared checks, and return sanitized evidence plus complete source ZIP/checksum. Do not perform a full project audit, feature work, source/test/Terraform fixes, dependency upgrades, deployments or broad reruns. This explicit limited assignment narrows the general implementation workflow below; the owner reviews and fixes findings. Heavy Windows laptop work is a last fallback after suitable remote options fail.

## Understand before changing

- Read START_HERE.md, delivery/HANDOFF_STATE.json, docs/PROJECT_HANDOFF.md, the complete docs/END_TO_END_STATUS.json register, docs/PRODUCTION_ACCEPTANCE.md and the affected implementation/runbooks.
- Continue ClipNest from the delivered source. Inspect the actual filesystem and Git state before assuming another chat's files exist. Do not replace this project with a new scaffold.
- Preserve the original 112 core task IDs. Domain/payment extras remain conditional and separately counted. Report evidence and remaining acceptance; never promote a task just because it has a filename or a mocked test.
- Application checkpoint CP-02 is version 1.2.0. H02 prepares bounded external verification and ownership/resource guidance; it is not a new production or application checkpoint. H01 is the preceding documentation/packaging snapshot.
- Distinguish the last application baseline commit from a later documentation/delivery commit and from the exact image/schema deployed. Never invent a commit or self-referential ZIP digest.
- Current identity is the implemented email/password/session/verification/reset lifecycle. A historical plan proposed Cognito; do not migrate identity or add a new identity provider without a product decision.

## Own the feasible work

- Implement and fix all feasible source, tests, docs and packaging. Missing AWS access alone does not block independent coding or local verification.
- Check capabilities in this environment. A model name does not grant Docker, shell, filesystem, account, network or browser access. Record concrete errors and a precise unblock step when execution is unavailable.
- Keep existing architecture and feature contracts unless observed evidence or an approved requirement justifies changing them. Do not spend a work session rebuilding code already present.
- Do not edit an applied SQL migration. Add a forward migration when necessary. Keep the CP-01 rollback incompatibility and deletion-after-restore obligations in view.
- Use authorized media and supported source behavior. A source restriction is a real failure. Do not disable TLS verification, import cookies, rotate networks or bypass source restrictions to turn it into a pass.
- Preserve owner-only Site access. The private static Site is not the AWS application. Keep AWS public launch behind the documented release gates.
- Proceed with authorized reversible work. For AWS account changes, billable resources, external messages, payments, DNS and public release, use the owner's actual established authorization; never guess credentials, account, recipient, spend or market permission.
- Keep credentials in the environment/secret manager. Do not put passwords, cookies, action links, signed URLs, connection strings, AWS keys, private PEMs, state or personal media in the repository, logs, ZIP or chat.
- No paid integration or custom domain is required for the free capped beta unless the owner selects that scope.

## Evidence and statuses

Use L (locally implemented), P (partially implemented), R (prepared, not executed), B (externally blocked), N (not started), preserving the register's definitions. Report all five counts, not a misleading implemented/remaining percentage.

Keep separate evidence for PGlite SQL, native PostgreSQL/pooling/TLS, injected AWS transports, actual AWS services, emulated DOM, real browsers/devices, synthetic fixture media and actual authorized source-to-device transfers. A skip is not a pass. An idle restart is not an active-job crash drill. A CloudFront POP or CodeBuild Region alone is not a real user transfer geography.

Only mark production evidence passed after the named check executes on the matching release source/image with retained results. The validator's references are pointers to reviewed evidence, not proof by themselves. Keep production NO_GO until all applicable gates and owner inputs pass.

## Every final project-work response

1. State the current goal/checkpoint and release decision.
2. Give updated L/P/R/B/N counts for the same 112 core IDs; list changes by ID with evidence and what remains.
3. Explain the implemented changes and relevant checks actually executed, including failures and skips.
4. Name each material blocker, exact missing capability/input, next action and owner. State what can still proceed independently.
5. Link the COMPLETE latest source ZIP and its SHA-256 checksum, updated full status, handoff and continuation prompt. Never deliver only a diff or claim a file exists without creating it.
6. Give the next useful implementation/execution actions. Update the handoff so the next model can continue from files without reading the old conversation.

After source/docs changes, run npm run package and the read-only verification mode. Keep scripts/package.py's included source directories/root files current if the project gains a directory or required file. Check that all distributable tracked source files are represented; exclude credentials, runtime data, old archives, caches and dependencies. Include .env.example, lockfiles, SQL migrations, tests, workflows, Terraform and its provider lock, public CA, runbooks and these handoff files.

Update docs/END_TO_END_STATUS.json and its human-readable form together when statuses change; mirror compact status without changing denominators. Increment the handoff revision after material changes. Run checks appropriate to the changes, then package final bytes and report their checksum. Do not fake a fresh test timestamp by copying historical results.

If no project files changed, provide the verified existing ZIP and explicitly say it is unchanged. If the environment cannot create/download files, report that limitation accurately and provide the latest verified artifact when accessible; do not fabricate a ZIP link. Intermediate progress messages can be brief without repackaging.
